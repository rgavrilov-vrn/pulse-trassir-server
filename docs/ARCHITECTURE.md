# Логика работы и хранение

## 1. Точки входа и модули
Collector и Sender — отдельные серверные скрипты TRASSIR, но не гарантированно разные процессы/интерпретаторы. SDK activate_on_events/timeout регистрируются в scripts/*.py. Импорт библиотечных модулей сам не запускает подписки.
Текущий Collector импортирует device_snapshot.CollectorApplication, который расширяет unified_snapshot.CollectorApplication; последний наследует базовый core.CollectorApplication. Импорты inventory/features используются для сериализации/SDK-текста/raw_sdk, а не для запуска старых циклов. Старые object_health/profiles/object_states остаются для истории.
core: ConfigManager, EventFactory, EventRepository, EventFileWriter, Application, CollectorApplication, SenderApplication, HttpTransport. features: Snapshot/SdkEventFactory и старый health-адаптер. inventory: общий сериализатор частей. unified_snapshot: сбор перечня и values. device_snapshot: паспорт/связи.

## 2. Запуск и конфигурация
Точка входа задаёт ROOT/sys.path, один раз перечитывает core -> features -> inventory -> unified_snapshot -> device_snapshot и создаёт новый app с settings, objects_list, SDK object. Перед этим прежние Collector/Sender должны быть остановлены: reload не отменяет callbacks и не обновляет старые экземпляры. Смешивание поколений классов Python 2 способно вызвать unbound method __init__.
Конфиг читается как UTF-8-sig. ConfigManager проверяет базовые настройки и не чаще раза в 5 секунд перечитывает файл из callback. При невалидном обновлении сохраняет предыдущий базовый снимок; при первом запуске невалидная базовая конфигурация останавливает создание приложения.
Настройки unified snapshot/raw_sdk и device-расширения валидируются дополнительными слоями. Невалидный слой сохраняет его предыдущие рабочие настройки; при старте они могут оставаться выключенными/пустыми. Это не общая атомарная валидация всех расширений: смотрите сообщения Unified snapshot settings rejected и Device snapshot settings rejected.

## 3. События SDK и файлов
SDK-подписка одна, на все типы/объекты. Обработчик проверяет collector.enabled, преобразует событие, фильтрует по исходному SDK data.type через exclude_event_types и сохраняет. Фильтр не является списком event_type наших периодических снимков. raw_sdk — дополнительная ограниченная диагностика атрибутов.
При периодическом tick базовый Collector обновляет конфиг, читает выбранные текстовые источники и создаёт heartbeat. На источник — до 100 частей по 64 КиБ за tick. Короткая строка без newline ждёт завершения, длинная может разбиться с chunked=true. Позиция файла/событие фиксируются вместе в SQLite. start_at применяется только при первом обнаружении source.id. Ротация распознаётся по st_dev/st_ino и уменьшению размера; быстрая copytruncate/rename может приводить к пропускам. Собственные логи/архив запрещены как вход.

## 4. Цикл единого снимка
1. Проверить enabled/срок следующего опроса.
2. Один раз objects_list(""); проверить форму (name,guid,class,parent), SDK-текст и уникальность GUID. Некорректные строки исключаются с отметкой неполноты, не превращаются в фиктивные объекты.
3. Разрешить локальный Server: явный GUID из конфигурации должен присутствовать среди Server. Автопривязка только при одном видимом Server. При неоднозначности health не копируется произвольно.
4. По классу собрать values: локальный Server health, Channel settings, выбранные state() других классов. Папки настроек внутри объекта кэшируются на проход; health-папка читается один раз у выбранного Server.
5. Для IP Device прочитать разрешённый паспорт и настроенные channelXX_guid; проверить ссылки на Channel текущего снимка; вычислить обратные ссылки/неоднозначности.
6. Обновить времена/полноту, отсортировать записи по GUID, сформировать один логический snapshot_id.
7. Измерить и разбить снимок на части; сохранить каждую через обычный save.

Выборка только read-only SDK-операций. Нет общего одновременного замера, неизменного SDK-снимка или deadline. Период — не realtime-гарантия. Callback планируется через timeout после завершения предыдущего; синхронный сбор может задерживать прочие события в общем Script Engine. RLock сериализует callbacks конкретного Collector, но не координирует два случайно запущенных Collector.
Snapshot-конвертер сохраняет scalars/UTF-8 текст и ограничивает сложные данные. Чтение с ошибкой даёт null плюс collection_errors, а не ноль/offline. collection_complete оценивает качество сбора, не здоровье устройства. Автоматических правил инцидентов/нормализации состояний нет.

## 5. Сохранение и SQLite
EventRepository хранит путь БД и threading.local; у каждого потока каждого экземпляра репозитория собственное соединение, созданное в вызывающем потоке. check_same_thread не отключается. journal_mode=DELETE, synchronous=FULL; synchronous задаётся новым соединениям. Ожидание блокировки 0.1 секунды, WAL не включён. Это устраняет передачу одного connection между потоками, не гарантирует отсутствие database is locked.
Событие -> INSERT events(status=pending) -> COMMIT -> одна попытка JSONL. Для файлового события checkpoint в offsets участвует в той же транзакции. Ошибка SQLite означает отсутствие файловой копии, возможна потеря SDK-события. Аварийного буфера нет. Ошибка JSONL не откатывает БД: предупреждение не чаще раза в минуту, повторного копирования нет.
Части одного снимка сохраняются отдельными транзакциями; сбой посередине оставляет неполный снимок. Приёмник не должен применять неполный перечень.

| Таблица | Назначение |
|---|---|
| meta(k,v) | schema=1 и identity=[server_id,destination_id,url] |
| events | UUID, JSON payload, Unix created, status, batch_id |
| batches | UUID, неизменный JSON HTTP-пакета, status, attempts, next_at, lease, owner, error, created, delivered |
| offsets | id источника и JSON состояния чтения файла |

Статусы events: pending -> batched -> delivered. quarantine — событие слишком велико для одиночного HTTP-пакета. Пакеты имеют pending/delivered; сетевые ошибки увеличивают attempts/next_at, не удаляют данные. queue_debug использует собственный dict-row_factory; основной репозиторий по-прежнему использует sqlite3.Row, риск Unicode-ключей Python 2 в Sender не исправлен одной утилитой.

## 6. Один tick Sender
1. Перечитать конфиг, при sender.enabled=false закончить.
2. BEGIN IMMEDIATE: найти старейший pending batch. Если next_at/lease ещё не истекли — ждать, новый пакет не формировать.
3. Если batch нет, выбрать до batch_size pending-событий по created, уложить полный HTTP JSON в max_batch_bytes. Слишком большое одиночное событие -> quarantine.
4. Сохранить payload/batch_id/sent_at, связать events с batch, выставить lease/owner, COMMIT.
5. Выполнить одну синхронную HTTPS-попытку вне транзакции.
6. Только HTTP 200: транзакционно пометить пакет/его события delivered. Иначе attempts+1, retry с jitter, снять lease.
7. Примерно раз в час выполнить ограниченную очистку старых delivered, если retention_days != 0.

Один плохой пакет блокирует последующие. Lease=max(120,timeout_seconds*20) секунд; не гарантия отсутствия сетевых дублей. Потеря ответа/падение после POST до finish ведёт к повтору сохранённых байтов. HTTP-тело ответа игнорируется. Ошибки 400/401/403 тоже не подтверждают данные и требуют оператора. Retry не имеет максимального числа попыток в текущей реализации.

## 7. Retention и эксплуатационные границы
Очистка удаляет до 100 delivered-пакетов за проход и их events. Pending/batched/quarantine автоматически по возрасту не удаляются. DELETE не уменьшает файл БД, VACUUM автоматически не выполняется. Нет квоты очереди, дискового backpressure или восстановления из JSONL.
Снимки и JSONL содержат инвентаризацию/IP/имена. Диагностический queue_debug дополнительно пишет полный payload пакетов; не используйте его как постоянный централизованный аудит.
При остановке TRASSIR агент тоже останавливается; пропавший heartbeat обнаруживает внешняя система. Текущий пилот подтверждает локальный сбор/разбиение, а не отказоустойчивость транспорта на всех серверах.
