# Расширенный мониторинг: первый этап

## Реализовано и что ещё нет
profiles.py добавляет три независимых read-only профиля к существующему Collector. Каналы: оба потока, запись, режим записи и health_ignore. Архив: глубина основного/дополнительного потока. IP Device: паспорт и настройки включённости.
Это НЕ завершение всех предложенных возможностей: связи channelXX_guid, текущее подключение IP Device, состав Template и агрегаты Folder пока не реализованы. Для Script/Template/Folder добавлен отдельный скрипт определения имён состояний; из наличия объекта не выводится online. Не читаются произвольные настройки и секреты.

## Включение
Остановите Collector/Sender, сохраните конфиг и согласованную копию БД, добавьте profiles.py рядом с остальными модулями. Замените содержимое серверного Collector новым scripts/collector.py, импорт теперь из profiles. Перенесите monitoring_profiles из config/monitoring_profiles.example.json в локальный config.json. Отдельный пример автоматически не читается и не заменяет ваш полный конфиг. Все три профиля выключены при отсутствии разделов. В примере они включены для пилота. enabled/interval_seconds/fields применяются динамически, интервал 10..86400 секунд. Параметры fields необязательны, по умолчанию все разрешённые поля профиля. Не меняйте server_id, URL, токен и БД.
Новые модули загружайте при остановленных обработчиках в порядке core -> features -> inventory -> object_health -> profiles, затем создавайте новый app. Reload не отменяет старые подписки.
Существующий objects_health с шестью полями остаётся независимым. После проверки channels_extended установите objects_health.enabled=false, чтобы избежать дублирования опроса. Серверный health и инвентаризацию это не выключает. Collector.enabled=false выключает всё.

## Профили и источники
channels_extended: agent.objects_health/event_version=1.1, data.profile=channels_extended. По всем Channel: flags.signal/recording_local/recording_hw, stats.fps_main/kbps_main/fps_ss/kbps_ss, info.grabber_error, корневые record_mode_local/health_ignore. Период по умолчанию 60 секунд.
channel_archive: тот же тип/версия, data.profile=channel_archive. arch_stats.mainstream_depth/substream_depth, период 600 секунд.
ip_devices: agent.devices_snapshot/event_version=1.0, data.profile=ip_devices. Все IP Device; корневые настройки ip_cameras/<GUID>: family, model, connection_ip, connection_port, grabber_enabled, channels_enabled, economy_mode, have_working_hdd. Период 900 секунд. Это паспорт, НЕ доказательство текущего соединения. Поля имени/класса/родителя берутся из objects_list. Логины, пароли и URL потоков не собираются; IP-адреса и названия являются чувствительной инвентаризацией, ограничьте доступ.
SDK-пути документированы, но их фактическая доступность/семантика на данной сборке требует пилотной проверки. Недоступные поля = null плюс collection_errors, не ноль и не offline. Отрицательные значения не преобразуются в bool. recording_local=0 без режима и расписания не является автоматически аварией; FPS дополнительного потока 0 без настройки включения не является автоматически неисправностью.

## Контракт и приём
HTTP-контракт остаётся 1.0, подтверждение только HTTP 200. Снимки используют общие snapshot_id/part_index/parts_total и objects[]. Каждый объект: object_id/name/class_name/parent_id, observed_at, metrics, collection_complete, collection_errors. В data: profile, object_class, source, scope=sdk_visible_class, общее число объектов/ошибок, requested_fields и время начала/конца; снимок не атомарный. Приёмник хранит последнее состояние отдельно по server_id + event_type + data.profile, иначе архивный профиль может затереть потоковые метрики. Применение только после получения всех частей; ошибки не означают удаление или нулевое значение. Сборщик использует разбиение inventory, не более min(64 КиБ, max_batch_bytes) на одиночный пакет. При частичной записи возможны неполные снимки. Защита от дублей по server_id+event_id.

## Диагностика Script/Template/Folder
Создайте ОТДЕЛЬНЫЙ одноразовый серверный скрипт из scripts/probe_object_states.py. Он не регистрирует подписки и не запускает таймеры. Читает один объект каждого класса и пытается получить имена его state через keys(), не значения, не методы управления. В logs/object_states_probe.log будут counts, sample_guid, тип state, state_keys либо error_type. Отсутствие keys() — результат диагностики, не основание включать неподтверждённые поля. Пришлите результат, чтобы выбрать поддерживаемый API; сам этот скрипт ничего не добавляет в очередь. Это диагностическое предположение о форме state, а не гарантированный интерфейс каждой сборки.
Для состава Template нужен подтверждённый источник членства (в том числе HTTP SDK /channels, если будет выбран такой адаптер). Для связи IP Device/Channel нужны фактические имена channelXX_guid вашей сборки. Для Folder нужны состав дерева и состояния каналов; вычисления пока не реализованы.

## Проверка и ограничения
В collector.log: Profile saved: profile=... objects=... parts=... errors=... complete=.... Проверьте JSONL каждого профиля и collection_errors до включения Sender. Опрос синхронный под общим RLock, последовательные профили могут задерживать SDK-события. Интервалы не являются строгим realtime-расписанием. Нет SDK deadline, нормализации времени и правил инцидентов. Существующий риск sqlite3.Row/Unicode в Sender не исправлен этим расширением. README/OPERATIONS описывают основу, особенности этой версии находятся здесь. Не объявляйте полный мониторинг всех классов завершённым до следующего этапа.
