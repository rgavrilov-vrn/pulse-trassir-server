# Развёртывание и сопровождение 1.0.0

## Статус и структура
Пилотная реализация Python 2.7.18 / SQLite 3.31.0. Внутри TRASSIR не проверена.
Исходники находятся только в src/trassir_agent; scripts — серверные точки входа.
Старые корневые camera_api.py, camera_status_monitor.py, config.py, logger.py,
server_events_collector.py НЕ относятся к новому проекту. Не запускайте их вместе
с новым Collector/Sender. Их физическое удаление — отдельная операция.
Архитектурные решения и контракт описаны в корневом README.

## Сборка и тесты
Из корня: python -m unittest discover -s tests -p "test_*.py"
Сборка: python tools/build.py
Результат: dist/trassir-sdk-agent-1.0.0.zip и .zip.sha256.
Используется явный список файлов. Секреты, локальная БД, логи, архив и config.json
не включаются. Сборка без pip и exe. Сценарии рассчитаны на Python 2.7/3.
Офлайн-тесты не заменяют запуск в SDK; проверяйте под целевым Python отдельно.

## Первая установка Windows
1. Распакуйте ZIP в C:/TRASSIR_Agent, сохранив src/, scripts/, config/, docs/.
2. Скопируйте config/config.example.json в config.json в корне установки.
3. Укажите уникальный server_id, destination_id и реальный HTTPS URL.
4. Создайте secrets/api.token с токеном в одной ASCII-строке. Установите ACL.
5. Разрешите пользователю TRASSIR запись в state/, logs/, archive/.
6. Создайте два серверных скрипта, вставив scripts/collector.py и scripts/sender.py.
7. Убедитесь в правильности ROOT в обеих точках входа. Запустите Collector.
8. Проверьте state/queue.db, archive/events.jsonl и logs/collector.log.
9. Запустите Sender; в примере enabled=false. Подготовьте приёмник.
10. Измените sender.enabled=true в config.json. Проверьте доставку и очередь.
Для Linux замените ROOT на каталог установки, используйте локальный диск.
Не запускайте два экземпляра одного SDK-скрипта.

## Конфигурация
Проверяется раз в 5 секунд при callback/tick. Неверный JSON/валидация сохраняют
последние корректные настройки. Заменяйте файл атомарно. Новые настройки
используются со следующего цикла. Токен/CA перечитываются при отправке.
Для storage нужен перезапуск. URL/server_id/destination_id привязаны к БД:
изменение требует явной миграции очереди; случайное изменение отвергается.
exclude_event_types действует на новые события. sender.enabled=false не
останавливает Collector. log_level управляет диагностикой.

## Реализованный контракт
Только 1.0; неизвестные версии отвергаются. JSON UTF-8.
Пакет: contract=trassir.telemetry, contract_version, batch_id, sent_at,
producer{name,version}, server{server_id}, events[].
Событие: event_id, event_type, event_version, occurred_at, observed_at, source, data.
Типы: trassir.system_event, trassir.log_entry, agent.heartbeat.
SDK ts сохраняется без предположений в timestamp_raw; occurred_at=null.
SDK p1/p2/p3 сохраняются JSON-скалярами или строками (не сложными SDK-объектами).
Это уточняет первоначальную рекомендацию README о приведении всего к строкам.
Версии: app 1.0.0, contract/event 1.0, config/DB/JSONL 1.
Для новой версии нужен новый сериализатор и тесты; смены строки недостаточно.
Только HTTP 200 подтверждает весь пакет; тело игнорируется. Приёмник обязан
атомарно сохранять все записи и дедуплицировать server_id+event_id.
Повтор — тот же payload/batch_id/sent_at. Возможны дубликаты при потере ответа.
Все не-200 и сетевые ошибки повторяются с backoff+jitter. В этой версии один
неуспешный пакет блокирует следующие. Исправляйте причины 400/401/403 на стороне
настроек/приёмника; бесконечно ожидающие пакеты автоматически не удаляются.

## SQLite и JSONL
Событие и checkpoint логов фиксируются одной транзакцией. Состояние доставки
в events.status: pending/batched/delivered/quarantine. Пакет в batches.
meta фиксирует схему и идентичность, offsets — позиции чтения логов.
После COMMIT одна попытка JSONL. Ошибка файла — warning не чаще раза в минуту,
без retry/отложенного архивирования. Ошибка БД — событие может потеряться,
файловой копии тогда нет. Это НЕ решение с гарантией сбора без потерь.
Локальный диск; DELETE journal, synchronous=FULL, ожидание блокировки 100мс.
HTTPS/JSONL вне транзакций. Соединения не передаются между потоками.
Архив: 10 MiB, 3 предыдущих файла. Не резервная копия диска.
Delivered удаляются через retention_days, 0 отключает удаление. Файл SQLite
не уменьшается сам: VACUUM только на остановленном проекте с запасом места.
Pending не имеют квоты, диск нужно мониторить. Quarantine — слишком большой
для одиночного пакета payload; исправление/возврат в очередь вручную после анализа.

## Файловые логи
collector.log_sources: [{"id":"main","path":"C:/REPLACE/server.log","encoding":"utf-8","start_at":"end"}].
Реальный путь/кодировку подтвердите на сервере. start_at только при первом чтении.
100 строк/источник/цикл, части строки до 64 KiB; длинные части помечены chunked.
Короткая строка без newline ждёт завершения. Ошибки декодирования заменяются.
Простая ротация: смена inode или уменьшение размера. Нет гарантированного
дочитывания переименованного файла; быстрый copytruncate может пропустить строки.
Windows inode требует проверки. Не подключайте выходные файлы агента/SQLite.

## Обновление, откат, эксплуатация
Остановите оба SDK-скрипта проверенным способом, сохраните конфиг/секреты и
согласованную копию SQLite, замените только код. Не затирайте runtime config,
state/, archive/, logs/, secrets/. Не полагайтесь на повторный import для
обновления модулей: необходима проверенная процедура перезапуска TRASSIR.
Миграции схемы не автоматизированы; несовместимый rollback запрещён.
Проверка очереди: SELECT status,count(*) FROM events GROUP BY status;
Ошибка доставки: SELECT id,attempts,error,next_at FROM batches WHERE status='pending';
Наблюдайте возраст очереди, диск, последнюю доставку и ошибки конфигурации.
Heartbeat отражает работу Collector, НЕ health TRASSIR. При остановке TRASSIR
сборщик не работает; внешняя система отслеживает отсутствие heartbeat.

## Ограничения и безопасность
HTTPS синхронный: второй SDK-скрипт не даёт процессной изоляции. Socket timeout
не общий deadline/DNS. Lease не исключает дубли при зависании дольше срока.
Фоновые потоки не добавлены без проверки их жизненного цикла SDK.
TLS проверяется системными CA или delivery.ca_file; verify=False отсутствует.
Токены/payload не печатаются в диагностике, но JSONL содержит данные событий.
Health, камеры, специализированная аналитика, квота диска, миграции БД и полная
обработка ротации не реализованы. Не включайте это в обещания production.
Пилот: проверить ev.*, timeout, SSL/CA, права, два соединения, медленный API,
перезапуск во время POST, сетевую изоляцию, ротацию и заполнение диска.
Только затем: 1 сервер -> малая группа -> примерно 100 серверов.
