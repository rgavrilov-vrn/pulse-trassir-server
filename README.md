# TRASSIR SDK Telemetry Agent

## Назначение и статус
Два серверных SDK-скрипта собирают системные события и выбранные текстовые логи TRASSIR и отправляют их во внешнюю систему по HTTPS. Целевые версии: Python 2.7.18 x64, SQLite 3.31.0; около 100 автономных видеосерверов. Приложение 1.0.0 — пилотная реализация, внутри вашей сборки TRASSIR ещё не проверена.

Исходники размещены. Старые корневые скрипты удалены. Сборочного сценария и каталога тестов нет по решению владельца: развёртывание обычным копированием, без pip, exe, внешней службы и брокера.

## Структура
```text
config/config.example.json     пример настроек
scripts/collector.py          серверная SDK-точка входа сбора
scripts/sender.py             серверная SDK-точка входа доставки
src/trassir_agent/core.py      классы приложения
src/trassir_agent/__init__.py  версия пакета
docs/OPERATIONS.md            сопровождение и ручные проверки
VERSION                      версия приложения
```
На сервере создаются локальный config.json, secrets/api.token, state/queue.db, archive/events.jsonl и logs/. Рабочие данные и секреты не публикуются в Git.

## Быстрый запуск
1. Скопируйте src/, scripts/, config/, docs/, README.md и VERSION в C:/TRASSIR_Agent, сохранив структуру. Можно использовать GitHub Download ZIP, распаковав содержимое корневой папки проекта. Дополнительная сборка не нужна.
2. Скопируйте config/config.example.json в C:/TRASSIR_Agent/config.json.
3. Задайте уникальный server_id, destination_id и реальный delivery.url.
4. Создайте secrets/api.token: одна строка ASCII-токена; ограничьте права файла.
5. Разрешите пользователю TRASSIR запись в state/, archive/, logs/ и чтение кода/настроек/токена.
6. Создайте два СЕРВЕРНЫХ скрипта в автоматизации TRASSIR, вставьте scripts/collector.py и scripts/sender.py. Проверьте ROOT в обоих. Для Linux замените ROOT на путь установки.
7. Запустите Collector и проверьте появление SQLite, heartbeat и JSONL.
8. Запустите Sender. По умолчанию sender.enabled=false. После проверки приёмника включите true в JSON и проверьте доставку.
Не запускайте старые/дублирующие экземпляры скриптов.

## Архитектура и классы
```text
SDK events + текстовые логи
          |
CollectorApplication -> SQLite COMMIT -> одна попытка JSONL
                              |
                      SenderApplication
                              |
                    сохранённый пакет -> HTTPS
                              |
                    HTTP 200 -> delivered
```
ConfigManager читает и проверяет настройки; EventFactory нормализует данные; EventRepository управляет событиями, пакетами и позициями логов; EventFileWriter создаёт дополнительную файловую копию; Application настраивает диагностику; HttpTransport выполняет HTTPS; CollectorApplication и SenderApplication координируют работу. Все реализованные классы находятся в core.py, дополнительные несуществующие адаптеры не подразумеваются.

SDK-функции activate_on_events и timeout вызываются только в точках входа. Подписка регистрируется один раз, фильтры меняются в обработчике. timeout использует миллисекунды и планируется повторно после каждого вызова. Сеть выполняется вне транзакций. Два скрипта SDK не равны двум изолированным процессам.

## Сохранение и SQLite
SQLite — источник истины. Событие и состояние pending создаются одной записью events; при чтении логов событие и checkpoint фиксируются одной транзакцией. После COMMIT — одна попытка JSONL и забыли. Ошибка файла не отменяет БД, повторного архивирования нет. При ошибке БД файловой копии нет и событие может потеряться.

Таблицы: events, batches, offsets, meta. Статусы событий: pending, batched, delivered, quarantine. Пакет, batch_id, sent_at и payload сохраняются до POST и не меняются при повторах. Один ожидающий пакет блокирует формирование следующих. Quarantine содержит события, не помещающиеся даже в одиночный пакет.

Локальный диск, отдельное соединение у каждого приложения, journal_mode=DELETE, synchronous=FULL, ожидание блокировки 100 мс. WAL не включён. Долгая блокировка может привести к ошибке сбора: гарантия сохранения всех событий при любых сбоях не заявляется. Нет аварийного spool, archive_status, повторного копирования или автоматического импорта архива.

Pending не удаляются автоматически, квота БД не реализована. Delivered очищаются порциями по retention_days; 0 отключает очистку. VACUUM не выполняется автоматически. Следите за диском и возрастом очереди.

## Файловое логирование
Диагностика: logs/collector.log и logs/sender.log, UTF-8, время/уровень/сообщение, traceback для ошибок обработчиков. Каждый активный файл примерно до 2 МиБ, до трёх предыдущих файлов; отдельная большая запись может превысить порог. log_level задаётся динамически.

Копия событий: archive/events.jsonl, UTF-8 JSON Lines, record_version=1; порог ротации 10 МиБ и три предыдущих файла. Ошибки копии логируются не чаще раза в минуту. Файл содержит данные событий, не актуальное состояние доставки и не полноценную резервную копию. Не подключайте собственные логи как входные источники.

## Конфигурация
Редактируется только локальный config.json. Проверка не чаще раза в 5 секунд при callback/tick; во время блокирующего запроса может быть позже. Неверный JSON/неподдерживаемая версия сохраняют последние корректные настройки. При первом старте неверный конфиг останавливает запуск. Используйте атомарную замену файла.

Основные настройки:
- collector: enabled, file_copy_enabled, tick_seconds, heartbeat_seconds, exclude_event_types, log_sources.
- sender: enabled, tick_seconds, batch_size, max_batch_bytes, retry_initial_seconds, retry_max_seconds, retention_days.
- delivery: destination_id, url, contract_version, token_file, ca_file, timeout_seconds.
- storage: database, archive, logs.
- config_version, server_id, log_level.

Отключение Sender не отключает сбор. Фильтры действуют только на новые события. Токен и CA перечитываются при попытке отправки. Storage требует перезапуска. Server_id, URL и destination_id привязаны к БД: менять их для накопленной очереди без явной миграции нельзя. Обычный reload не обновляет Python-код.

Пример текстового источника в collector.log_sources:
```json
[{"id":"main","path":"C:/REPLACE/server.log","encoding":"utf-8","start_at":"end"}]
```
Путь и кодировку подтвердите на сервере. Start_at действует при первом обнаружении id. Читается до 100 частей по 64 КиБ на источник за цикл. Короткая незавершённая строка ждёт newline. Уровень сообщения не угадывается. Ротация определяется только по идентичности файла/уменьшению размера; возможны пропуски при быстрой copytruncate или переименовании без дочитывания.

## Контракт 1.0
HTTPS POST, Content-Type: application/json; charset=utf-8; Authorization: Bearer из файла. Единственное подтверждение — HTTP 200 для ВСЕГО пакета. Тело ответа игнорируется. 201/202/204, другие коды и сетевые ошибки не подтверждают данные. Приёмник обязан вернуть 200 только после атомарного надёжного сохранения всего пакета.

```json
{
  "contract": "trassir.telemetry",
  "contract_version": "1.0",
  "batch_id": "b532e2f9-313d-4c6f-87f1-c141756a9bd4",
  "sent_at": "2026-11-09T07:00:00.000Z",
  "producer": {"name": "trassir-sdk-agent", "version": "1.0.0"},
  "server": {"server_id": "video81"},
  "events": [{
    "event_id": "e83dd902-96d8-4fca-9d94-c88427516e5e",
    "event_type": "trassir.system_event",
    "event_version": "1.0",
    "occurred_at": null,
    "observed_at": "2026-11-09T06:59:58.000Z",
    "source": {"object_id": "JFnVgcxe", "object_name": "Вход"},
    "data": {"type": "Signal Lost", "timestamp_raw": null, "p1": null, "p2": null, "p3": null}
  }]
}
```
Типы: trassir.system_event, trassir.log_entry, agent.heartbeat. observed_at/sent_at — UTC с Z. Пока единицы ev.ts не подтверждены, occurred_at=null, оригинальное значение в timestamp_raw. data SDK нормализуется в JSON-скаляры либо текст; bytes декодируются с заменой неверных UTF-8.

Доставка допускает повторы. Приёмник дедуплицирует server_id+event_id. Потеря ответа или сбой Sender после 200 до COMMIT означают повтор того же пакета. Exactly-once не заявляется. Retry — экспоненциальная задержка с jitter +/-20%; итоговая пауза может превысить retry_max_seconds на 20%. Ошибки 400/401/403 тоже не удаляют пакет: исправляет оператор.

## Версии и расширение
Независимые версии: приложение 1.0.0 (VERSION и пакет); contract_version=1.0; event_version=1.0; config_version=1; схема БД meta.schema=1; JSONL record_version=1.
Minor контракта — необязательные обратно совместимые поля. Major — несовместимое изменение структуры, типов или смысла. Реализация поддерживает только 1.0, новая версия требует кода, не смены строки в JSON. Сначала приёмник поддерживает старую и новую версии, затем обновляются Sender, затем переключаются новые пакеты. Уже сохранённые пакеты автоматически не переписываются.

## Обновление и ограничения
Остановите оба скрипта, сохраните конфиг, секреты и согласованную копию SQLite, замените код без перезаписи рабочих данных. Обновлённые SDK-точки входа также перенесите в TRASSIR. Используйте проверенную процедуру перезапуска: повторный import может оставить старый модуль. Автоматических миграций схемы нет; несовместимый откат запрещён.

HTTPS синхронный, timeout — сокетный, не общий deadline/DNS. Lease не исключает повторы при долгом зависании. TLS проверяется, verify=False нет. Установите права на токены и JSONL. Не логируйте Authorization и полный payload.

Health, камеры, специализированная аналитика, квота диска, гарантированная обработка ротации и восстановление истории не реализованы. Heartbeat означает жизнь Collector, не здоровье видеосервера. Если TRASSIR остановлен, сборщик тоже не работает; пропадание heartbeat отслеживает внешний сервис.

## Ручная приёмка
Проверьте на одном сервере Python/SQLite/SSL, ev.*, timeout, права, получение реальных событий, применение конфига, ошибки TLS/токена, недоступный API, повтор после перезапуска, конкуренцию SQLite, полный диск и ротацию логов. Только затем разворачивайте на малой группе и остальных серверах. Каталог автоматических тестов удалён по запросу; это не отменяет ручную проверку.
Подробные операции и SQL: [docs/OPERATIONS.md](docs/OPERATIONS.md).
