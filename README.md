# TRASSIR SDK Telemetry Agent

## Статус
Идёт замена старого проекта. Этот коммит фиксирует требования и документацию; он не означает, что новый исходный код уже размещён или проверен в TRASSIR. Старые файлы не являются реализацией описанной архитектуры. Развёртывание допускается после размещения исходников, тестов и сборочного сценария и прохождения пилота.

## Назначение и среда
Сбор системных событий и выбранных файловых логов примерно со 100 видеосерверов TRASSIR и доставка во внешнюю систему по HTTPS. Каждый сервер автономен. Целевые версии: встроенный Python 2.7.18 x64 и SQLite 3.31.0. Архитектура на классах с передачей зависимостей. Внешняя служба, pip-пакеты и брокер сообщений не требуются. Два серверных SDK-скрипта не означают два изолированных процесса.

## Зафиксированные решения
1. Collector сохраняет событие и состояние доставки в SQLite одной транзакцией.
2. После COMMIT один раз пытается записать JSONL и забывает. Ошибка файла не отменяет БД; архивирования с повторами, archive_status, аварийного spool и автоматического восстановления из файла нет.
3. Если запись в БД не удалась, файловую копию не создаём; фиксируем ошибку. Возможна потеря события.
4. Sender читает только SQLite и отправляет фиксированные пакеты.
5. Только HTTP 200 означает приём ВСЕГО пакета. Ответное тело игнорируется. Контракта подтверждения и частичного ACK нет. 201/202/204 не успех.
6. SQLite — источник истины. JSONL — дополнительная диагностическая копия, не полноценная резервная копия.
7. Настройки JSON перечитываются динамически; исполняемый config.py не используется.

## Архитектура
CollectorApplication: TrassirEventCollector, LogFileCollector, EventFactory, EventRepository, EventFileWriter, ConfigManager.
SenderApplication: OutboxRepository, BatchBuilder, ContractRegistry, HttpTransport, DeliveryWorker, ConfigManager.

Поток: SDK callback -> нормализация -> SQLite COMMIT -> best-effort JSONL. Независимо: SQLite -> сохранение HTTP-пакета -> HTTPS вне транзакции -> отметка delivered при 200. Для одного приёмника состояние доставки можно хранить в events; отдельная deliveries нужна при нескольких независимых получателях.

Подписка activate_on_events("", "", callback) регистрируется в точке входа один раз. Фильтры меняются внутри обработчика. SDK-функции не предполагаются автоматически доступными в импортируемых модулях. timeout использует миллисекунды и требует повторного планирования; time.sleep в SDK-цикле не используется. Не выводить message на каждое принятое событие: возможна обратная петля журнала.

## Хранилище
Таблицы: events — нормализованные события и состояние доставки; batches — зафиксированные пакеты, попытки и lease; offsets — позиции чтения логов; meta — версия схемы и идентичность сервера/приёмника.

Отдельное соединение у каждого скрипта/потока. Транзакции короткие. HTTPS и JSONL вне транзакций. SQLite на локальном диске. Начальный режим DELETE, synchronous=FULL, ограниченное ожидание блокировки; WAL не включать автоматически без проверки старой библиотеки и рекомендаций производителя. Ошибка блокировки не должна приводить к бесконечному ожиданию callback.

Статусы событий: pending, batched, delivered, quarantine. Слишком большое даже для одиночного пакета событие изолируется, не исчезает. Pending автоматически не удалять. Для очереди нужны мониторинг размера, возраста и свободного места и согласованная политика переполнения. Retention распространяется только на delivered. VACUUM — отдельная операция при остановленных скриптах.

## Контракт 1.0
Пакет JSON: contract=trassir.telemetry; contract_version=1.0; batch_id UUID; sent_at UTC; producer={name,version}; server={server_id}; events=[...].

Событие: event_id UUID; event_type; event_version=1.0; occurred_at; observed_at; source; data.
Типы первой версии: trassir.system_event, trassir.log_entry, agent.heartbeat.
Системное событие: source.object_id/source.object_name; data.type, timestamp_raw, p1, p2, p3. Неизвестные значения null; параметры нормализуются в строки либо null. Пока единицы ev.ts не подтверждены, occurred_at=null, исходное время в timestamp_raw.
Запись лога: data.source_id, level, message, chunked. Не угадывать уровень и время, если парсер отсутствует.
UTC-время формата YYYY-MM-DDTHH:MM:SS.sssZ. UTF-8. Content-Type: application/json; charset=utf-8. Авторизация Bearer из отдельного файла.

Приёмник обязан вернуть 200 только после надёжного атомарного сохранения всех записей. При частичном приёме 200 недопустим. Дедупликация по server_id+event_id. Повторные доставки возможны при потере ответа или падении Sender после 200 до локального COMMIT. Гарантия exactly-once не заявляется.

Повторная попытка сохраняет batch_id, sent_at, payload и event_id. Все не-200 и сетевые ошибки оставляют данные недоставленными. Backoff с ограничением и jitter. В первой простой реализации один неуспешный пакет может блокировать следующие; оператор исправляет причину, данные автоматически не выбрасываются.

## Версионность
Версия приложения, contract_version, event_version, config_version, версия схемы БД и record_version файлового JSONL независимы. Начальные: приложение 1.0.0, контракт 1.0, событие 1.0, конфиг 1, БД 1, JSONL 1.
Minor контракта — необязательные обратно совместимые поля; major — изменение смысла/типов/обязательных полей или правил приёма. Новая строка в конфиге не создаёт поддержку версии: нужен сериализатор. Неподдерживаемая версия отклоняется. Переход: приёмник поддерживает обе версии -> обновление Sender -> включение версии для новых пакетов -> завершение старых очередей. Зафиксированные пакеты не переписывать автоматически.

## Конфигурация
Обязательные разделы: config_version, server_id, collector, sender, delivery, storage. Collector: enabled, file_copy_enabled, tick interval, exclude_event_types, log_sources. Sender: enabled, interval, batch_size, max_batch_bytes, retry limits, delivered retention. Delivery: destination_id, HTTPS URL, contract_version, token_file, ca_file, timeout. Storage: database, archive, diagnostic logs.

Проверка изменений примерно раз в 5 секунд при вызове обработчика/таймера. Ошибка JSON/валидации сохраняет последнюю корректную конфигурацию. Конфиг менять атомарной заменой файла. Один цикл использует один снимок настроек. Отключение Sender не отключает Collector. Фильтры влияют на новые события. Изменение storage требует перезапуска; server_id/приёмник привязаны к БД. Смену URL нельзя автоматически применять к накопленной очереди: нужна явная миграция.

## Плановая структура и сборка
src/trassir_agent/ — общие классы; scripts/ — две SDK-точки входа; config/ — пример; tests/ — тесты; tools/ — сборка и проверки; docs/ — подробные руководства; schemas/ — контракт. dist/ — генерируемые ZIP и checksum, не исходники.
Сборка должна копировать только runtime, SDK-скрипты, пример настроек и документацию; не включать токены, БД, логи, архивы и локальный config.json. Никакой компиляции в exe не требуется. Не заявлять готовую команду сборки до размещения сценария.

## Развёртывание и сопровождение
План установки: собрать ZIP -> распаковать в C:/TRASSIR_Agent -> создать локальные настройки и файл токена -> дать права TRASSIR -> создать два серверных скрипта -> запустить Collector -> проверить SQLite/JSONL -> запустить Sender с отправкой disabled -> проверить URL/TLS -> enabled=true.
Обновление: сохранить конфиг и очередь, остановить скрипты, сделать согласованную копию SQLite, заменить код без перезаписи секретов/данных, выполнить миграцию при необходимости, перезапустить проверенным способом. Простая повторная команда import не гарантирует загрузку нового модуля. Откат к несовместимой схеме БД недопустим без восстановления согласованной копии.

Ротация файловых логов требует проверки реальной схемы: переименование, copytruncate, кодировка, длинные и незавершённые строки, особенности inode Windows. Собственные логи агента нельзя подключать как вход. Позицию чтения и событие фиксировать одной транзакцией.

## Безопасность и ограничения
Проверка TLS обязательна; verify=False не использовать. Файлы токенов ограничить правами. Не логировать Authorization, токены и полный payload. JSONL может содержать чувствительные данные. Python 2.7 и старая SQLite требуют оценки поддерживаемых обновлений TRASSIR, самовольно библиотеку не подменять.
HTTPS первой реализации синхронный: отдельный SDK-скрипт не гарантирует изоляции. Socket timeout не равен общему deadline запроса/DNS. Фоновые потоки допустимы лишь после проверки SDK lifecycle. Lease не гарантирует отсутствие повторов при долгом зависании. Не запускать дубликаты Collector/Sender.
Health и камеры не выдавать за реализованные до проверки SDK. Heartbeat означает работу сборщика, не здоровье видеосервера. При остановленном TRASSIR сборщик не работает; внешний сервис определяет пропадание по heartbeat. Восстановление всей истории без проверенного исторического API не обещается.

## Приёмочные проверки
Офлайн: 200/не-200, неизменность повторного пакета, ошибка сети, ошибка файловой копии без rollback, ошибка БД без файла, неверный reload, checkpoint, lease. На сервере: Python/SQLite/SSL imports, ev.*, timeout, права, нагрузка и блокировки, медленный HTTPS, перезапуск во время отправки, полный диск, ротация, истёкший токен/сертификат.
Массовое внедрение только после пилота и проверки реального приёмника. Этапы: 1 сервер -> малая группа -> остальные. Наблюдать возраст/размер очереди, последнюю доставку, ошибки, свободный диск и версию активного конфига.
